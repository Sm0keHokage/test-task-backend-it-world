# Платформа приёма платежей - тестовое задание

Реализация тестового задания на позицию Middle Backend Developer (Python/Django).
Оригинальный текст задания сохранён в [`TASK.md`](./TASK.md).

Стек: Python 3.11, Django 5.0, PostgreSQL 16, без DRF (чистые `django.views` +
`JsonResponse`), бонус - отдельный сервис курсов на FastAPI.

---

## Как поднять проект

```bash
cp .env.example .env
docker compose up -d --build
```

Поднимаются три контейнера:

| Сервис | Порт на хосте | Назначение |
|---|---|---|
| `db` | `5434` | PostgreSQL |
| `web` | `8010` | Django, миграции применяются автоматически при старте |
| `rates` | `8011` | FastAPI-сервис курсов (бонус) |

Нестандартные порты - осознанно: на многих машинах уже занят системный
Postgres на `5432`, а `8000`/`8001` часто конфликтуют с другими локальными
проектами.

Проверить, что всё работает:

```bash
curl -s http://localhost:8010/api/v1/merchants/1/balance/ -H "X-Api-Key: <ключ проекта>"
curl -s http://localhost:8011/health
```

### Тесты

```bash
python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
python -m pytest
```

Тесты по умолчанию гоняются на sqlite in-memory (`config/settings_test.py`,
`pytest.ini`) быстро, без необходимости держать поднятым `docker compose`.
Один тест (`test_concurrency.py`) на sqlite осознанно пропускается -
гонки проверяются только через реальные построчные блокировки Postgres,
на sqlite это была бы фикция, а не проверка:

```bash
docker compose up -d db
DATABASE_URL=postgres://payments:payments@localhost:5434/payments \
    DJANGO_SETTINGS_MODULE=config.settings \
    python -m pytest billing/tests/test_concurrency.py -v
```

### CI

`.github/workflows/ci.yml` - на каждый push/mr в `dev`/`main` поднимает
настоящий Postgres как service-контейнер и гоняет весь набор тестов
против него (`DJANGO_SETTINGS_MODULE=config.settings`, а не
`settings_test`) - включая тест на гонку, который локально по умолчанию
пропускается на sqlite. Плюс `manage.py check` и
`makemigrations --check --dry-run` (ловит забытую миграцию после правки
модели).

## Архитектурные решения

**Слои.** Views ничего не знают о бизнес-правилах: парсят запрос, вызывают
одну функцию из `services.py`, мапят результат/исключение на HTTP-код через
`errors.error_response()`. Вся логика - в `services.py`, единым модулем:
домен тесно связан через FK (Merchant -> Project -> Invoice ->
Payment/LedgerEntry), дробление на искусственные Django-приложения ради
дробления добавило бы косвенности без пользы на таком размере кода.

**Аутентификация - декораторы, не middleware.** `@require_project_api_key`
и `@require_internal_token` (`billing/auth.py`) вешаются на конкретные
views. При 5 эндпоинтах с разными схемами авторизации декоратор явный и
локальный; middleware пришлось бы ветвить по `request.path`. Оба декоратора
несут `csrf_exempt` - это API на заголовочной аутентификации, а не форма с
сессией, CSRF-защита для него не имеет смысла.

**Идемпотентность в двух местах:**
- Создание счёта - `UNIQUE(project_id, merchant_external_id)` + перехват
  `IntegrityError` при гонке двух одновременных запросов.
- Обработка платежа - `UNIQUE(invoice_id, provider_transaction_id)`, тот же
  паттерн.

**Гонки за один и тот же счёт** закрыты `select_for_update()` внутри
`transaction.atomic()`. Проверено не только на словах: тест
`test_concurrency.py` был прогнан с временно убранной
`select_for_update()` - падал в большинстве прогонов (задвоенные проводки),
с ней - стабильно зелёный. Это же теперь автоматически перепроверяется в CI
на каждый push.

**Баланс мерчанта не хранится** - вычисляется как
`SUM(LedgerEntry.amount) GROUP BY merchant_id, currency`, обслуживается
индексом `(merchant_id, currency)`. Строка-счётчик слишком легко
рассинхронизировать с реальными проводками.

**Конвертация валют.** Курс фиксируется на `Payment.exchange_rate_used` в
момент поступления, не пересчитывается на лету - исторический отчёт не
меняется при обновлении курсов. Источник курса: сначала БД-снапшот
(`ExchangeRate`), при отсутствии - внешний сервис (бонус). Вызов идёт **до**
входа в `transaction.atomic()`/`select_for_update()` - сетевой запрос не
должен держать блокировку строки `invoice`.

**Просрочка** - батчами по id без `OFFSET` (обработанные строки сами
покидают фильтр), не более `batch_size` записей в памяти одновременно -
безопасно на 100k+ строк. Гонка с одновременной оплатой закрыта не
блокировкой, а семантикой Postgres: `UPDATE ... WHERE status IN (...)`
перепроверяет условие после ожидания чужой блокировки.

**Уведомления - transactional outbox.** `NotificationDelivery` создаётся в
той же транзакции, что и сам терминальный переход статуса
(paid/overpaid/cancelled/expired). HMAC-SHA256 подпись тела в заголовке
`X-Webhook-Signature`, ключ - `Project.webhook_secret`. Экспоненциальный
backoff (1мин/5мин/30мин/2ч/6ч), после 6 попыток - `failed` для ручного разбора.
Доставка - at-least-once, не exactly-once (фундаментальное ограничение
HTTP, а не недоработка): мерчанту стоит дедуплицировать по
`invoice_id`+`status` из тела.

**Отчёт - два запроса, не один с JOIN.** Invoice-агрегаты и
LedgerEntry-агрегаты считаются раздельно и сводятся по ключу группы
(день/project_id) в Python - на количестве групп, а не счетов. Один
JOIN Invoice->Payment->LedgerEntry размножил бы строки (fan-out) и задвоил
суммы. Проверено на 20 000 засеянных счетах через `EXPLAIN ANALYZE` -
запросы укладываются в единицы миллисекунд.

**Бонус (a): сервис курсов на FastAPI.** `rates_service/` - отдельный
процесс, `GET /rates?currency_from=&currency_to=` с in-process TTL-кэшем.
Django ходит туда через `billing/rates_client.py` (stdlib `urllib`, таймаут
2с), при недоступности - единое исключение `RatesServiceUnavailable` ->
`422` клиенту, без 500 и без зависаний. Полученный курс сохраняется как
снапшот в БД - повторные запросы той же пары больше не бьют по сети.

## Допущения

Задание намеренно оставляет несколько мест неоднозначными:

1. **`new`/`pending`** - `pending` не используется как отдельное состояние;
   частичная оплата это `underpaid`.
2. **Терминальность `underpaid`/`overpaid`** - `underpaid` не терминален
   (можно донести до `paid`), `overpaid` терминален.
3. **Граница paid/overpaid** - «совпадает» трактуется как «переплата ≤1%»
   (иначе недостижимо при конвертации валют из-за округления курса).
4. **База комиссии при overpaid** - считается от фактически полученной
   суммы, а не от номинала счёта.
5. **«Курс на момент поступления»** - снапшот в БД, с фолбэком на внешний
   сервис (реализован как бонус), а не обязательный синхронный запрос при
   каждом платеже.
6. **Защита `/internal/payments/`** - отдельный сервисный токен платформы
   (не `X-Api-Key` мерчанта, у провайдера его и не должно быть); платёж от
   заблокированного мерчанта фиксируется как факт поступления денег, но не
   зачисляется на баланс.

## Что не сделано / как бы доделал

- **Формальные тесты для `rates_service/` (FastAPI)** - проверено вживую
  через `curl` и полный сквозной сценарий из Django, но отдельного
  `pytest`+`TestClient` для самого FastAPI-приложения нет.
- **Доставка вебхуков - HTTP-вызов внутри транзакции с блокировкой строки**
  (`billing/notifications.py`). Для редкого запуска management-командой это
  приемлемо; для высоконагруженного воркера правильнее разнести на
  «захватить -> закоммитить -> сделать запрос -> отдельная транзакция на
  результат». Реальный планировщик (Celery beat/cron) для
  `expire_invoices`/`deliver_notifications` не настроен - команды готовы к
  вызову по расписанию, сам cron/beat не описан инфраструктурно.
- **Функциональный индекс под отчёт** - EXPLAIN показал, что фильтр по дате
  транслируется Django в вычисляемое выражение
  (`(created_at AT TIME ZONE 'UTC')::date`), из-за чего композитный индекс
  `(project_id, created_at)` не используется по второй колонке. На текущем
  объёме не проблема (единицы мс); при росте на порядки - завести
  `CREATE INDEX ... ON invoice (((created_at AT TIME ZONE 'UTC')::date))`.
- **Ротация/отзыв API-ключей и webhook-секретов** - не реализована
  (создание Project/Merchant - через admin/shell, вне API-части задания).
