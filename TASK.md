## Легенда

Мы делаем платформу для приёма платежей за онлайн-услуги.

Мерчант (наш клиент) регистрирует у нас проект и через API выставляет счёт своему покупателю. Покупатель оплачивает счёт — иногда одним платежом, иногда несколькими, иногда не полностью, иногда с переплатой, иногда в другой валюте. Платформа фиксирует поступления, ведёт баланс мерчанта, удерживает комиссию и уведомляет мерчанта о результате.

Нужно реализовать ядро этой платформы.

## Технические требования

- Python 3.11+, Django 4.2 или 5.x
- PostgreSQL
- **DRF использовать нельзя.** HTTP-слой — на обычных Django views (`django.views.View`, `JsonResponse`). Это осознанное ограничение: нам важно увидеть, как вы строите API-слой руками.
- `docker compose up` — и проект поднимается вместе с БД, миграции применяются
- Тесты обязательны (pytest или встроенный unittest) — минимум на бизнес-логику из части 3
- Линтер/форматтер на ваш выбор, но пусть будет

Библиотеки для валидации, конфигов, тестов и всего остального — свободно. Ограничение только на DRF.

## Часть 1. Модель данных

Спроектируйте и реализуйте схему. Ниже — сущности и их смысл, конкретные поля и связи вы определяете сами.

| Сущность | Смысл |
|---|---|
| **Merchant** | Наш клиент. Может быть активен или заблокирован. |
| **Project** | У мерчанта может быть несколько проектов. У проекта свой API-ключ и свой URL для уведомлений. |
| **Invoice** | Счёт: сумма, валюта, статус, срок жизни, идентификатор на стороне мерчанта. |
| **Payment** | Поступление по счёту: сумма, валюта, идентификатор транзакции, время. Поступлений по одному счёту может быть несколько. |
| **LedgerEntry** | Движение по балансу мерчанта: зачисление, удержание комиссии и т.д. |
| **ExchangeRate** | Курс валютной пары на момент времени. |

**Что важно:**

- Деньги — только `Decimal` с фиксированной точностью. Никаких `float`.
- Ограничения целостности живут в БД, а не только в Python: `unique`, `unique_together`, `CheckConstraint`, индексы под реальные запросы из части 4.
- Баланс мерчанта не должен быть изменяемым полем, которое можно случайно рассинхронизировать. Считайте его из проводок. Если решите денормализовать ради скорости — обоснуйте в README и покажите, как защищаетесь от расхождения.
- Статусы счёта опишите явным конечным автоматом: какие переходы разрешены, какие нет, где это проверяется. Базовый набор: `new`, `pending`, `paid`, `underpaid`, `overpaid`, `expired`, `cancelled` — можете скорректировать, если считаете нужным, но объясните почему.

## Часть 2. HTTP API

Все эндпоинты — на обычных Django views.

| Метод | Путь | Что делает |
|---|---|---|
| `POST` | `/api/v1/invoices/` | Создать счёт |
| `GET` | `/api/v1/invoices/{id}/` | Счёт: детали, список поступлений, остаток к доплате |
| `POST` | `/api/v1/invoices/{id}/cancel/` | Отменить счёт |
| `POST` | `/internal/payments/` | Зафиксировать поступление (эмуляция колбэка от платёжного провайдера) |
| `GET` | `/api/v1/merchants/{id}/balance/` | Баланс мерчанта в разрезе валют |

**Требования:**

- Аутентификация публичных эндпоинтов — по заголовку `X-Api-Key` проекта. Внутренний эндпоинт защищён отдельно (как — на ваше усмотрение, опишите решение).
- Создание счёта идемпотентно по идентификатору на стороне мерчанта: повторный запрос с тем же идентификатором в рамках проекта возвращает уже созданный счёт, а не дубль и не 500.
- Единый формат ответа об ошибке и осмысленные HTTP-коды. Валидация входных данных — на ваш выбор инструмента, но объясните выбор в README.
- Во views не должно быть бизнес-логики. Где она живёт и почему именно там — ваше архитектурное решение.

## Часть 3. Бизнес-логика

Это центральная часть задания, на неё смотрим внимательнее всего.

### Обработка поступления

- Повторный колбэк с тем же идентификатором транзакции не должен создавать второе поступление и второй раз двигать баланс.
- Сумма поступлений меньше суммы счёта → счёт `underpaid`, в ответе GET видно, сколько осталось доплатить.
- Сумма совпадает → счёт `paid`, деньги зачисляются на баланс мерчанта.
- Переплата больше 1% от суммы счёта → счёт `overpaid`, но зачисляется вся фактически полученная сумма.
- Поступление в валюте, отличной от валюты счёта → конвертация по курсу на момент поступления. Курс, по которому посчитали, должен сохраняться вместе с поступлением, чтобы отчёт за прошлый период не «поехал» при обновлении курсов.
- Два колбэка по одному счёту, пришедшие одновременно, не должны ломать статус счёта и баланс мерчанта.

### Комиссия

Платформа удерживает с каждого успешно оплаченного счёта **1%, но не менее 0.50** в валюте счёта. Комиссия — это отдельная проводка в ledger, а не «вычли из суммы и забыли».

### Просроченные счета

Management-команда, которая переводит неоплаченные счета с истёкшим сроком в `expired`.
Требования: команда идемпотентна (повторный запуск ничего не ломает) и не падает по памяти на 100 000 записей.

## Часть 4. Отчёт

```
GET /api/v1/merchants/{id}/report/?date_from=&date_to=&group_by=day|project
```

По каждой группе вернуть:

- количество выставленных счетов
- количество оплаченных
- сумму выставленную
- сумму фактически полученную
- сумму удержанной комиссии
- конверсию в оплату

**Требования:**

- Данные собираются одним-двумя запросами к БД. Цикл по счётам с догрузкой связанных объектов — не подходит.
- Приложите к README вывод `.query` или `EXPLAIN` для основного запроса и два-три предложения о том, почему запрос выглядит именно так и какие индексы его обслуживают.

## Часть 5. Уведомления мерчанта

Когда счёт переходит в терминальный статус, мерчанту нужно отправить уведомление на URL из настроек проекта, подписанное HMAC.

Минимально ожидаем: модель доставки уведомления со статусами, схему повторных попыток и то, как вы гарантируете, что уведомление не потеряется и не уйдёт дважды. Реальный воркер (Celery, RQ, management-команда — на ваш выбор) — плюс, но можно ограничиться заглушкой и описанием схемы в README.

## Что оцениваем

1. **Модель данных** — нормализация, целостность на уровне БД, работа с деньгами и валютами.
2. **Бизнес-логика** — корректность граничных случаев, идемпотентность, поведение при гонках.
3. **Запросы** — понимание того, что происходит в БД, отсутствие N+1, осмысленные индексы.
4. **Архитектура** — где границы слоёв, насколько легко добавить новый сценарий.
5. **Тесты** — покрыты ли неочевидные случаи, а не только happy path.
6. **Инженерная зрелость** — читаемость, коммиты, README, честность про недоделанное.
